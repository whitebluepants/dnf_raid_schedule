# DNF 米歇尔团本排表工具设计规格

## 1. 背景与目标

本项目为固定小团体提供一个多人在线使用的 DNF 团本排表工具。一个游戏账号下可以有多个角色，但同一时刻只能登录一个角色；同一角色在一个游戏周内只能参加一次米歇尔团本，普通、困难和审判难度共享该次数。

一次开团活动包含多波团次。每波最多 12 个角色，分为红、黄、绿三队，每队默认由 1 个奶和 3 个 C 组成。同一时间只进行一波，因此同一账号可以在不同波次使用不同角色，但同一账号不能在同一波出现两次。

第一版的目标是：

- 团员登录后维护自己的账号和角色资料，并报名本次可用角色。
- 团长或管理员创建活动及多波团次，为每波选择普通、困难或审判难度。
- 系统根据角色强度和硬约束生成尽量多的完整波次初稿。
- 团长通过拖拽、交换、锁定和候补推荐快速调整初稿。
- 多人同时查看时能够实时看到更新，并避免并发覆盖。
- 使用托管数据库持久化数据，部署后无需自建域名和服务器。

## 2. 第一版范围

### 2.1 包含

- 邮箱和密码注册、登录、退出和重置密码。
- 首次注册后填写游戏昵称，并输入团体邀请码加入团体。
- 团员、团长、管理员三种权限。
- 玩家、账号、角色的分层管理。
- 角色类型、名望、强度档位、模拟伤害或奶量参考值。
- 每次活动的角色报名与成员整场缺席状态。
- 活动、波次和可扩展难度配置。
- 半自动生成排表。
- 桌面端拖拽与移动端点击交换。
- 波次、队伍和角色槽位锁定。
- 候补池、风险提示、临时缺席和替换建议。
- 排表草稿、发布状态、实时查看和调整历史。
- 数据库行级权限和乐观并发控制。
- Vercel 与 Supabase 部署。

### 2.2 不包含

- 精确到场时间或“仅参加第几波”的时间段管理。
- QQ、微信或其他第三方登录。
- 根据职业平衡、装备细节、实战操作自动判断真实强度。
- 在线文档式逐字符协同编辑。
- 自动读取 DNF 客户端或助手数据。
- 自动替团长发布完全不可修改的最终答案。

## 3. 用户与权限

### 团员

- 查看本团体已发布的活动和排表。
- 创建和维护自己的游戏账号、角色及强度数据。
- 为一次活动勾选本周可参与的角色。
- 将自己标记为本次参加或缺席。
- 不能修改其他成员资料或排表。

### 团长

- 拥有团员全部权限。
- 查看全体成员的报名角色。
- 创建和管理活动、波次与排表。
- 运行半自动排表、锁定位置、拖拽调整、处理临时缺席。
- 发布排表并记录发布后的变更。

### 管理员

- 拥有团长全部权限。
- 管理团体资料、邀请码、成员角色和团长权限。
- 管理难度及红黄绿队参考配置。

权限由 Supabase Row Level Security 在数据库层强制执行，前端隐藏按钮只用于改善体验，不能作为安全边界。

## 4. 技术架构

- 前端与服务端：Next.js App Router、TypeScript。
- UI：Tailwind CSS 和可访问的无头组件；拖拽使用支持鼠标、触摸和键盘的库。
- 表单与校验：客户端即时校验，服务端使用同一套 schema 再次校验。
- 认证：Supabase Auth，第一版使用邮箱和密码。
- 数据库：Supabase PostgreSQL。
- 实时更新：Supabase Realtime 订阅活动、报名和排表变更。
- 部署：Vercel Hobby 项目，使用自动生成的 `vercel.app` HTTPS 地址。
- 数据迁移：所有表、索引、约束、RLS 和种子配置均保存在版本化 SQL 迁移中。

前端不持有数据库服务密钥。普通读写使用用户会话和 RLS；需要跨用户写入或原子处理的操作通过服务端接口执行。

## 5. 核心数据模型

### `profiles`

与 Supabase Auth 用户一一对应，保存游戏昵称和基础展示信息。

### `groups` 与 `group_members`

保存团体、邀请码摘要、成员关系及 `member`、`leader`、`admin` 角色。邀请码只保存不可逆摘要，并允许管理员轮换。

### `game_accounts`

保存成员名下的游戏账号。第一版允许一个成员维护多个账号，以兼容后续实际情况。

### `characters`

保存角色名、职业、角色类型、名望、强度档位、模拟伤害、奶量参考值、备注和数据更新时间。

- 角色类型：`dealer`、`buffer`。
- 强度档位：`high`、`medium`、`low`。
- 模拟伤害只对 C 参与辅助排序。
- 奶量参考值只对奶展示和辅助排序。
- 名望和强度档位是自动初排的主要参考，团长可以手动覆盖最终位置。

### `difficulty_presets`

保存普通、困难、审判及未来难度。每个难度包含入场最低名望、各队 C 参考名望、各队奶参考值、模拟伤害参考线和是否启用自动分配。所有阈值均由管理员配置，不写死当前社区传言。

### `raid_events`

表示一次开团活动，包含标题、游戏周标识、活动日期、状态和创建人。状态包括 `draft`、`open`、`published`、`completed`、`archived`。

### `raid_waves`

表示活动中的一波，包含顺序、难度、状态和版本号。同一活动可以混合普通、困难和审判。

### `event_registrations`

保存成员是否参加本次活动及报名版本号。一个成员在一次活动中只有一条记录。

### `event_character_registrations`

保存成员为本次活动勾选的可用角色。报名角色必须属于该成员，一个角色在一次活动中只能勾选一次。角色库长期保留，团员无需每周重新录入资料。

### `schedule_slots`

保存波次、队伍颜色、队内位置、已分配角色及锁定状态。每波固定 12 个逻辑槽位：红黄绿三队，每队 1 个奶位和 3 个 C 位。

### `character_weekly_usage`

记录角色在游戏周内 `reserved` 或 `completed` 的团本使用状态。排入有效波次时原子创建预约记录；从排表移除且尚未通关时释放预约；团长确认通关后转为完成状态。普通、困难和审判共享唯一约束，确保一个角色一周只能使用一次。

### `schedule_revisions`

记录自动生成、拖拽、交换、替换、缺席和发布等操作前后的摘要，用于审计、撤销和识别发布后变化。

## 6. 数据库硬约束

- 同一游戏周内，同一角色最多出现在一个有效波次。
- 同一波内，同一游戏账号最多出现一次。
- 同一槽位最多分配一个角色。
- 角色只能由所属成员维护；管理员纠错操作必须写入修订记录。
- 只有团长或管理员可以修改排表和难度配置。
- 已归档活动只读。

奶/C 位置不做不可绕过的数据库限制，因为临时开荒可能需要非常规队伍；服务端默认阻止不匹配操作，团长确认后可以保留异常编成，并显示红色风险提示。

## 7. 半自动排表

### 7.1 输入

- 活动中已创建的波次及其难度。
- 团员本次报名的可用角色。
- 角色类型、名望、强度档位、模拟伤害或奶量参考值。
- 难度配置的参考阈值。
- 已锁定的波次、队伍、槽位和角色。
- 本游戏周已经使用的角色。

### 7.2 硬约束优先级

1. 同一角色在同一游戏周不能重复。
2. 同一账号在同一波不能重复。
3. 一个槽位只能有一个角色。
4. 默认每波需要 3 奶和 9 C。
5. 锁定内容不能被重新生成覆盖。

### 7.3 软目标优先级

1. 最大化完整波次数量。
2. 困难度更高的波次优先获得合格配置。
3. 尽量满足难度和红黄绿队参考线。
4. 红队强度高于或等于黄队，黄队高于或等于绿队。
5. 尽量安排更多已报名角色，避免无理由长期留在候补区。

### 7.4 第一版算法

第一版使用可解释的贪心算法，不引入约束求解器：

1. 保留全部锁定内容并验证是否存在硬冲突。
2. 按难度优先级和波次顺序处理未锁定波次。
3. 先按奶的强度档位、奶量参考值和名望分配 3 个奶。
4. 再按 C 的强度档位、名望和模拟伤害辅助分配 9 个 C。
5. 在满足账号约束的前提下，将较强角色优先放入红队，其次黄队和绿队。
6. 无法完成的槽位保留为空，并生成缺口原因与候补建议。

自动生成永远保存为可编辑草稿。再次生成时，用户可以选择保留锁定内容；系统不会静默覆盖团长已完成的手工调整。

## 8. 排表交互

### 桌面端

- 中间区域按波次展示红黄绿三队。
- 侧边栏展示候补角色，可按成员、账号、C/奶、档位和难度适配度筛选。
- 角色卡展示角色名、成员、账号、名望、档位和模拟伤害或奶量。
- 支持候补到槽位、槽位到候补、跨队拖拽及两个角色直接交换。
- 拖拽悬停时预览替换结果和风险。

### 移动端

- 不依赖精细拖拽。
- 先点选一个角色，再点目标槽位完成移动或交换。
- 波次使用折叠卡片，当前编辑波次保持展开。

### 锁定与历史

- 支持锁定整波、单队、槽位或角色。
- 支持撤销和重做当前编辑会话中的操作。
- 服务端保存修订记录；页面刷新后可以查看历史并恢复到选定版本。

## 9. 风险提示

- 绿色：满足队伍结构和参考配置。
- 黄色：允许保存，但低于团长设置的软参考线或数据较旧。
- 红色：缺奶、角色周次数重复、同波账号重复、角色不属于报名池或并发数据已变化。

红色硬冲突默认阻止发布。非常规奶/C 队伍属于可确认的红色编成风险，而角色重复和同波账号重复属于不可绕过的数据库冲突。

## 10. 临时缺席

团长将成员标记为本次缺席后：

- 该成员已安排位置保留占位信息并显示红色缺口。
- 该成员角色从候补池隐藏，但不删除长期角色资料。
- 系统为每个缺口推荐符合角色类型、难度和账号约束的替代者。
- 团长可以一键替换或手动调整。
- 系统不会自动重排其他已完成波次。
- 取消缺席后，角色重新进入候补池，但不会自动抢占已有位置。

## 11. 实时协作与冲突处理

团员主要修改自己的角色和报名；团长主要修改排表，因此通过数据所有权减少真正的写冲突。

- 页面订阅当前活动、报名和排表变更并实时刷新。
- 排表写入携带记录版本号，服务端执行乐观锁检查。
- 如果另一位团长已先修改同一槽位，后提交者收到明确冲突提示，并看到服务器最新状态。
- 跨槽位交换、替换及角色周次数变更在同一数据库事务中完成。
- 发布操作验证整个活动的硬约束和当前版本，防止发布过期草稿。
- 实时订阅只改善反馈速度；数据库约束和事务负责最终正确性。

## 12. 主要页面

1. 登录、注册和重置密码。
2. 首次加入团体和个人资料设置。
3. 我的账号与角色。
4. 活动列表与本次报名。
5. 团长排表工作台。
6. 已发布排表查看页。
7. 成员与权限管理。
8. 难度和门槛配置。
9. 排表历史与变更记录。

## 13. 错误与异常处理

- 网络中断时保留未提交的表单内容，并提供明确重试按钮。
- 数据库冲突不静默覆盖，显示冲突位置和最新数据。
- 自动排表失败时返回可读原因，如奶数量不足或账号约束导致无法组成完整波次。
- 实时连接中断时显示“正在重新连接”，恢复后主动刷新当前活动。
- 服务端日志记录请求标识和错误类别，但不记录密码、令牌或邀请码原文。
- 页面使用局部错误边界，单个角色或波次数据异常不应导致整个工作台不可用。

## 14. 测试策略

### 单元测试

- 自动排表硬约束和软排序。
- 游戏周角色唯一性。
- 同波账号唯一性。
- 奶/C 数量与候补推荐。
- 锁定内容保持不变。

### 数据库测试

- 唯一索引、事务函数和状态转换。
- 团员、团长、管理员的 RLS 权限。
- 并发交换、发布和缺席操作。

### 组件测试

- 角色表单和校验。
- 风险标记、锁定和候补筛选。
- 点击交换与撤销、重做。

### 端到端测试

- 注册、加入团体、添加角色和报名。
- 创建 `7困难 + 1普通` 活动并生成初稿。
- 团长拖拽调整并发布。
- 第二位用户实时看到发布结果。
- 临时缺席后推荐并完成替换。
- 两位团长同时修改同一槽位时正确提示冲突。

### 部署验证

- Vercel 生产构建通过。
- 生产环境变量齐全且不暴露服务密钥。
- Supabase 迁移、RLS 和 Realtime 配置生效。
- 注册、登录、排表、实时更新和退出在生产地址完成冒烟测试。

## 15. 部署与运维

- 代码仓库连接 Vercel，主分支提交自动生成生产部署。
- Supabase 项目保存认证和业务数据。
- 环境变量区分本地、预览和生产环境。
- 数据库变更只能通过迁移执行，禁止只在网页控制台手工修改而不留版本记录。
- 第一版使用 Vercel 自动域名；未来可无代码改动绑定自有域名。
- 发布前导出一次数据库结构；上线后定期导出业务数据，弥补免费计划备份能力有限的问题。

## 16. 后续演进

- 精确到场时间和指定波次可用性。
- 审判难度上线后的独立阈值与规则。
- 从实际手工调整历史中改进自动排序权重。
- QQ、微信等第三方登录。
- DNF 助手数据导入。
- 通关结果、炸团记录和角色周次数的更完整闭环。
- 自定义队伍模板和其他团本支持。

后续功能均建立在现有可扩展难度、活动、波次、角色和修订模型之上，不改变第一版的核心权限与数据所有权。
